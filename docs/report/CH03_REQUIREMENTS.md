## 3.1 Introduction

This chapter formally defines the requirements of the Finance Tracker system. It begins with a stakeholder analysis, presents functional and non-functional requirements, and closes with use-case and data-flow analysis. The requirements were gathered through a combination of self-study of existing personal finance applications, personal need assessment, and review of the Nepal fintech landscape described in Chapter 2.

**Table 3.2 — Non-Functional Requirements**

| ID | Category | Requirement |
|----|----------|-------------|
| NFR-01 | **Security** | All API endpoints (except login/register/CSRF) shall require valid JWT authentication |
| NFR-02 | **Security** | Passwords shall be hashed with BCrypt (strength 10) |
| NFR-03 | **Security** | JWTs shall be stored in HttpOnly Secure cookies to prevent XSS |
| NFR-04 | **Security** | All state-modifying requests shall include a valid CSRF token |
| NFR-05 | **Security** | Every database query shall be scoped to the authenticated user's ID |
| NFR-06 | **Security** | Account lockout shall trigger after 5 failed logins |
| NFR-07 | **Performance** | Transaction list pages shall load within 2 seconds for up to 10,000 records |
| NFR-08 | **Performance** | Database queries shall use indexed columns (user_id, dates, types) |
| NFR-09 | **Scalability** | The application shall be stateless and horizontally scalable |
| NFR-10 | **Reliability** | JWT tokens shall be revocable via a `revoked_tokens` table |
| NFR-11 | **Maintainability** | All database schema changes shall use versioned Flyway migrations |
| NFR-12 | **Maintainability** | Backend code shall maintain >80% unit/integration test coverage on critical paths |
| NFR-13 | **Portability** | The full application stack shall be deployable with a single `docker compose up` command |
| NFR-14 | **Usability** | The UI shall be responsive across desktop, tablet, and mobile viewports |
| NFR-15 | **Data Integrity** | `DECIMAL(15,2)` shall be used for all monetary values (no floating point) |
| NFR-16 | **Compatibility** | The application shall function on Chrome 120+, Firefox 120+, and Safari 17+ |
| NFR-17 | **Internationalisation** | NPR and at least 10 major currencies shall be supported |

### 3.5.3 Key Use Case Detail — UC-06: Transfer Between Accounts

**Actor:** Registered User  
**Pre-condition:** User is logged in; source and destination accounts both exist.  
**Main Flow:**
1. User navigates to "New Transaction" and selects type "Transfer."
2. User selects source account, destination account, amount, and date.
3. System creates two linked transaction records:
   - A debit on the source account (EXPENSE-like debit).
   - A credit on the destination account (INCOME-like credit).
4. Both account balances update atomically.
5. Both transactions appear in respective account views, linked to each other.

**Post-condition:** Net-worth is unchanged; account balances reflect the transfer.  
**Exception:** If source account balance is below transfer amount (for non-credit accounts), a validation error is returned (informational only — overdrafts are permitted in the current implementation for simplicity).

### 3.5.4 Key Use Case Detail — UC-13: Automated Recurring Transaction

**Actor:** System Scheduler  
**Pre-condition:** At least one active recurring transaction template has `next_occurrence <= today`.  
**Main Flow:**
1. Spring Scheduler triggers daily at midnight (configured via `@Scheduled`).
2. System queries all active recurring templates where `next_occurrence <= CURRENT_DATE`.
3. For each template, a new transaction is created using the template's details.
4. `last_processed_date` is updated to today.
5. `next_occurrence` is advanced by the template's frequency.
6. A notification is created for the user informing them of the auto-created transaction.

**Post-condition:** Transaction(s) created; account balance(s) updated; `next_occurrence` advanced.

## 3.6 Data Flow

### 3.6.1 Authentication Data Flow

```
Browser → POST /api/v1/auth/login (username, password)
         → Spring Security filters → AuthService.login()
         → BCryptPasswordEncoder.matches()
         → JwtTokenProvider.generateToken()
         → ResponseCookie (HttpOnly, Secure, SameSite=Strict)
         → 200 OK + Set-Cookie: auth_token=<jwt>
```

On subsequent requests:
```
Browser (auto-sends auth_token cookie) → JwtAuthenticationFilter
→ JwtTokenProvider.validateToken()
→ SecurityContext populated with UserPrincipal
→ Controller method @AuthenticationPrincipal UserPrincipal resolved
```

### 3.6.2 Transaction Creation Data Flow

```
User fills form → React Hook Form validates (Zod schema)
→ apiClient.post('/api/v1/transactions', payload)   [adds X-XSRF-TOKEN header]
→ nginx /api/* proxy → Spring Boot
→ CSRF filter validates X-XSRF-TOKEN
→ JwtAuthenticationFilter authenticates user
→ TransactionController.createTransaction()
→ TransactionService.createTransaction(userId, request)
→ TransactionRepository.save(transaction)
→ AccountService.updateBalance(accountId, amount, type)
→ TransactionMapper.toResponse(savedTransaction)
→ 201 Created + TransactionResponse JSON
→ TanStack Query cache invalidated → UI re-renders with new transaction
```

## 3.7 Constraints

| Constraint | Description |
|-----------|-------------|
| **Time** | Development completed within one academic semester |
| **Platform** | Must run on standard developer hardware (8GB RAM, any OS) |
| **No External APIs** | Exchange rates stored statically; no paid third-party API required |
| **Docker required** | Production deployment assumes Docker; bare-metal deployment is possible but undocumented |
| **No native mobile** | Browser-based only; no React Native or Flutter app in scope |
